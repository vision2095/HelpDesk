# Reference comparison — 18 October 2026

This is a finite feature inventory from public pages and available artifacts, not a claim that private paid functionality or every reference behavior has been observed. LensDesk is an original implementation. Marketing assertions are not acceptance evidence.

Research used the requested agent-reach skill: Jina Reader for public pages and `gh` for GitHub. REA is already connected, with the reference repository present in the parent workspace. No duplicate plugin installation was necessary. The agent-reach CLI is absent; its documented direct backends were used. No third-party account was created and no paid service was purchased.

- [HintLens homepage and setup instructions](https://hintlens.com/) describe Windows-only C++, profiles/resume/JD, screenshot questions, system audio, overlay, configurable shortcuts, custom prompts, multiple providers, typing, cloud history/PDF, multilingual responses and web search.
- [HintLens interview page](https://hintlens.com/interview) describes live contextual suggestions and adaptive feedback. Its universal invisibility and speed statements are unverified marketing claims.
- [Evadus homepage](https://evadus.net/) describes Windows-only AI chat, screenshots, BYOK, paid screen sharing/remote access, gifts, community documentation and support. The V.L.I.D HDMI device is a separate unreleased hardware proposal.
- [Evadus public lite repository](https://github.com/Evadus-wtf/evadus-lite) describes a Windows WPF/WebView2 browser, licensed GPL-3.0. It is not evidence of the complete paid application's internals. Its code was not copied into LensDesk.
- The public Evadus `/docs` route returned a community payment article, not a complete application manual. It does not establish full UI or runtime behavior.
- Two public HintLens Windows ZIP downloads have different member names but identical executable bytes: 2,128,384 bytes; SHA-256 `0eb36faba51525379e5dee67c981e8b6493497e4065f6a3f68ad442ef7d9801b`. Archive hashes differ. REA classified the executable as native PE x86_64, without .NET metadata. This is static classification, not recovered original source or observed Windows execution. No original executable was run.

## Capture findings

[Electron documentation](https://www.electronjs.org/docs/latest/api/browser-window#winsetcontentprotectionenable-macos-windows) states that macOS ScreenCaptureKit applications can capture a window despite `setContentProtection(true)`. On Windows Electron uses WDA_EXCLUDEFROMCAPTURE; support differs by Windows version. [Microsoft's documentation](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowdisplayaffinity) also describes limited API coverage rather than a universal guarantee.

On this macOS 27 host, direct native tests of false → true → false returned `isContentProtected() === true` each time. LensDesk therefore exposes the saved setting, the applied request and the OS-reported flag separately. A true reported flag is not a successful screenshot-exclusion test. Native E2E validates request propagation across startup/toggle/floating/reload, not invisibility in every recorder.

The installed user's capture preference was off. After enabling it and confirming the applied request/native flag, CUA's bound-app screenshot returned a blank frame while its accessibility tree still exposed the window. This demonstrates exclusion through that particular capture route only. Zoom, Teams, OBS and OS screen-recording behavior have not been measured here. Existing customized shortcut values were left persisted; UI automation attempts to restore defaults did not produce a verified saved change and are not counted as a fix.

REA also inspected the installed Electron framework fuse bytes (evidence `ev_5d50cb37676c098461e41b33114b3a610930c5a2a2188c90834ba8e31bdf0036`). The inspected pre-update app permits Node/Inspector flags and lacks embedded ASAR integrity enforcement. Publisher release hardening remains a gap; this does not by itself demonstrate exploitation.
